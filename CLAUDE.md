# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

This is `lib` (module `github.com/Raccoon-CI/lib`), the shared library of Raccoon CI, a self-hosted CI/CD platform that moves GitHub Actions workflows onto compute the user chooses. The library is data and protocols: the workflow parser and expression evaluator, the catalog of tool knowledge, the wire and dispatch protocols between a controller and a machine, the job graph, the InstaBox client, and the artifact/cache protocol services. It runs nothing itself and has no `main` package.

It was split out of the monorepo `raccoonci` (history kept). Nothing here may depend on the other repositories.

## Depends on / used by

- Depends on nothing of ours: standard library and third-party modules only.
- Used by `raccoonci-runner` (the machine side and the local engine), `cli` (through the runner) and `backend` (the server). Dependency direction: lib <- runner <- cli, and lib <- backend. The backend must never import the runner or cli.

## Module list

`pkg/` (public): `value`, `expr`, `workflow`, `trigger`, `cron`, `catalog`, `runnerimages`, `platform`, `wire`, `dispatch`, `runevent`, `jobgraph`, `instabox`, `blob`, `artifact`, `cache`, `archive`, `affected`, `sched`, `ghrunner`. `internal/` (private helpers): `azblob`, `twirp`. `deploy/catalog-feed` is the template of the `Raccoon-CI/catalog` repository, not Go code.

No API is promised stable yet (0.x); see `TODO.md`.

## Developing across the repositories

`v0.1.0` of this library is published (tag on `main`), and the other repositories require it, so each one builds on its own with a plain `go build ./...`. To try a change to lib in `runner`, `cli` or `backend` before releasing it, put the four checkouts side by side and add a `go.work` next to them with a `use` line for each directory; the workspace then overrides the published version. Do not commit that `go.work`. This repository has no sibling dependency, so `go mod tidy` is fine here. A release is a new tag (`v0.1.x`) on `main`; the other repositories then bump their `require`.

## Layout and dependency guards

- `pkg/<pkg>/`: public packages. `pkg/deps_test.go` fails if a package under `pkg/` depends, even transitively, on anything of this module other than `pkg/*`, `internal/azblob` and `internal/twirp`. The packages `wire`, `runevent` and `jobgraph` have stricter guards of their own (data packages only: `runevent` rests on `value` only; `wire` on `runevent` and `value`; `jobgraph` on `catalog`, `expr`, `platform`, `runevent`, `value`, `workflow`). Keep the guards green; when a guard has to change, change its allow-list on purpose, never by loosening it to pass.
- `internal/azblob`, `internal/twirp`: the library's own private helpers for `artifact` and `cache`.
- `deploy/catalog-feed`: template of the `Raccoon-CI/catalog` repository (the signed catalog feed).

## Architecture

**Knowledge that changes as tools evolve belongs in `pkg/catalog/catalog.yaml`, not in Go code.** This covers:
- which commands belong to which toolchain, tool or apt package
- setup actions and their inputs
- version-file formats
- where the runner-images report states the defaults
- which Node.js major each `runs.using` runs on
- runner labels to OS (`ubuntu-*` → linux), which OSes are available, and the tracked runner images with their labels and toolset files
- the machine's own platform (Debian 13 / trixie) and the Ubuntu-to-Debian warnings (`lsb_release`, PPAs)
- how wrapper commands (`sudo`, `env`, `timeout`) and package installers (`apt-get install`) are read

Code holds only the mechanisms: parsers for the file formats it names, the report walker, the shell parser. When adding support for a tool, edit the YAML. A Go change is only needed for a new *kind* of rule.

What stays in code on purpose is GitHub's own protocol, which changes with GitHub's releases, not with the tool ecosystem: workflow and `action.yml` keys, workflow command names, expression syntax, shell command lines, and limits such as 256 matrix jobs. Download locations (GitHub, nodejs.org) also stay in code, because the catalog may come from the network and must not be able to redirect downloads.

The catalog is layered: built-in, then a feed pulled from `-catalog-url` (cached on disk, refreshed daily with ETag, optional ed25519 signature), then the local file. Because it may come from the network, a catalog only *names* things: every name is checked against a strict character set, and it cannot hold commands or URLs. A failed pull never stops a run: it falls back to the cache and then to the built-in one, and says why on stderr.

- `pkg/value`: the dynamic data model shared by the parser and the expression evaluator. Values are nil/bool/float64/string/[]any/`value.Object`. `Object` is an *ordered* key list, because matrix expansion order and GitHub's generated job names depend on key order. All numbers are float64, matching GitHub (so `3.10` becomes `3.1`, as it does there). `value.Decoder` walks `yaml.Node` trees with a shared node budget, which guards against alias bombs in untrusted PR workflow files. Use one Decoder per document.
- `pkg/workflow`: `Parse` turns workflow YAML into `Workflow`/`Job`/`Step`. Fields that may be literals or `${{ }}` expressions stay as raw `any` values and are evaluated later. Like GitHub, it rejects unknown keys, missing `runs-on`/`steps`, bad needs and cycles. `ExpandMatrix` implements GitHub's include/exclude rules and takes an already-evaluated matrix; dynamic matrices (`${{ fromJSON(...) }}`) must go through the evaluator first. The matrix tests encode the examples from GitHub's docs, so keep them passing.
- `pkg/expr`: a hand-written lexer, parser and evaluator for `${{ }}`, following GitHub's documented semantics: mismatched types compare as numbers, strings compare case-insensitively, `&&`/`||` return operands, `*` object filters, and objects/arrays are equal only to the same instance. `Interpolate` keeps the type of a lone `${{ x }}` (so `false` stays falsy and `fromJSON` can build a matrix) and stringifies mixed text. `EvalCondition` adds the implicit `success() &&` and treats mixed text as an always-true string, as GitHub does. A missing context returns `*expr.UnknownContextError`, which `plan` uses to defer values that are only known at run time.
- `pkg/runnerimages`: what GitHub's hosted Ubuntu images preinstall (default tool versions, toolcache versions, apt packages, CLIs), so jobs that rely on preinstalled tools get the same versions here. `Fetcher.Latest` reads the *fully deployed* release from runner-images' README status badge (a gist, not the API: no token, no 60/hour limit). It falls back to the releases API (newest non-prerelease) when the badge is missing, malformed, or names a version whose report can't be downloaded. Data per release comes from the `internal.<image>.json` release asset, plus the toolset at the same tag for Go's default. Which images exist, their labels and toolset file names come from the catalog, and `ubuntu-latest` is resolved from the README table (`Snapshot.Aliases`, written to `aliases.json`). `Snapshot.ForLabel(cat, label)` needs the catalog. The embedded `snapshot/` is the offline fallback. The planned server will poll the same sources into its database. Only send the token to api.github.com.
- `pkg/catalog`: loads and validates `catalog.yaml`. The file is embedded, and `Overlay` applies another catalog on top: same-name entries replace, `name: null` removes, top-level lists replace. Validation rejects:
  - unknown keys
  - a command claimed by two entries
  - references to undefined toolchains
  - unknown version-file formats
  - names with characters that could inject options or paths (`-o…`, `../`)
  - bad regexps and unknown message placeholders

  A catalog with a higher `schema` than the code understands is refused as a whole (`ErrNewerSchema`). `TestDefaultIsValid` guards the embedded file. `Source` (`source.go`) pulls a feed:
  - https only, no redirect downgrade
  - size-capped
  - conditional requests with ETag
  - the cache is rewritten only after the new file has been verified and validated
  - cached content is re-verified on every read, so a tampered cache file is ignored
- `pkg/blob`: where artifact bytes live. `Store` is a small interface (multipart `BeginUpload`, `PresignGet`, `Stat`, `Delete`) shaped for the planned artifact service: a block is forwarded as one part without landing on disk, and downloads are presigned URLs that bypass our server. `Dir` implements it on a local directory (downloads go through `Dir.Handler`, with HMAC-signed links), for single-machine runs. `S3` implements it with the official `aws-sdk-go-v2` for any S3-compatible store (`Endpoint` + `PathStyle` for MinIO, R2 and the like). Checksums are set to "when required" because many compatible stores reject the SDK's default CRC trailers, and parts are sent with an unsigned payload because their hash isn't known up front. Unit tests run against an in-process fake S3. `TestRealS3` (skipped unless `RACCOONCI_TEST_S3_ENDPOINT`, `_KEY`, `_SECRET` are set) was run against SeaweedFS's S3 gateway, including a wrong-secret check; MinIO no longer publishes binaries or images. AWS itself has not been tried.
- `pkg/artifact`: the artifact protocol of `upload-artifact`/`download-artifact` v4+, so they run unchanged. Two halves, as on GitHub. Metadata is the Twirp `ArtifactService` (Create, Finalize, List, GetSignedArtifactURL, Delete, JSON only) at `ACTIONS_RESULTS_URL`, authenticated by `ACTIONS_RUNTIME_TOKEN`, an HS256 JWT whose `scp` claim `Actions.Results:<run>:<job>` is what the toolkit reads. A token opens only its own run, and only its own job may create. Data is a small imitation of Azure Blob: `CreateArtifact` returns a signed URL on our server, and an `azblob.Upload` behind it receives the SDK's calls (see `internal/azblob`). Downloads need no imitation: the store's presigned URL is returned. FinalizeArtifact checks the stored size against the client's; the client's sha256 is recorded and returned as `digest`, not verified. Metadata is in memory, and in an optional `Index` (`Config.Index`: `Load` at start, `Save` when an artifact is finalized, `Delete`) that the server backs with its database; without one a restart forgets it, as `raccoonci run` does. `Config.Keep`/`MaxKeep` set the default time to keep and cap what a client asks for; `Service.Expire`, `Artifacts` and `DownloadURL` serve the server's sweep and API. `raccoonci run` starts the service on a loopback port with a `blob.Dir` under the workdir, and also on a job network's gateway for container jobs (see `internal/runner`). Verified end to end with the real `upload-artifact@v4` and `download-artifact@v4` (20 MB, three blocks, two jobs). Not done: artifact v3 (REST), per-job tokens (a local run uses one token for all jobs), retention enforcement in `raccoonci run` (the server sweeps).
- `internal/azblob`: receives one blob from a client that thinks it is talking to Azure Blob Storage, and writes it into a `blob.Store`. One `Upload` sits behind one signed URL and implements the calls `@azure/storage-blob` makes: Put Block and Put Block List (files the SDK sends in blocks), and Put Blob (files small enough for one request; `@actions/cache` v2 sends up to 128 MiB that way). If the first block id has the SDK's shape (`base64(36-char prefix + 12 digits)`), block i is forwarded as part i+1 of a multipart upload without touching disk, and the block list must be exactly 0..n-1 in order (unlisted blocks are dropped, as Azure does). Any other id shape takes a spool path: blocks wait on disk and are cut into `partSize` parts at commit. The first request fixes the mode, and a blob written with Put Blob refuses blocks (409). An empty blob is refused. A repeated Put Blob that already succeeded is a no-op, since clients retry after a lost reply.
- `internal/twirp`: the shared parts of the Twirp JSON protocol (errors with their HTTP status, replies, and a request reader that accepts snake_case or camelCase names and 64-bit integers as strings). Used by the artifact and cache services.
- `pkg/cache`: the cache protocols of `actions/cache` and the `cache:` option of `setup-*`. v1 is REST under `/_apis/artifactcache/` at `ACTIONS_CACHE_URL` (`GET cache`, `POST caches`, `PATCH caches/{id}`, `POST caches/{id}`), same runtime token as artifacts. v2 is the Twirp `CacheService` (CreateCacheEntry, FinalizeCacheEntryUpload, GetCacheEntryDownloadURL) at `ACTIONS_RESULTS_URL`: CreateCacheEntry hands out a signed upload URL, an `azblob.Upload` receives the data, and Finalize turns the upload into an entry. Refusals (the entry exists, another job is saving it, wrong size) are ordinary replies with `ok: false` and a `message`, because the client reads those; only malformed requests and server faults are Twirp errors. Both protocols are always served and share one set of entries, because the client computes `version` the same way in both. Which one the client uses is decided by `ACTIONS_CACHE_SERVICE_V2`: `Env` sets it to `true` when `Config.AdvertiseV2` is on (`raccoonci run -cache-protocol v2`) and clears it otherwise, so a value inherited from the host cannot switch the client. The toolkit uses v1 unless that variable is set. Upload URLs of v2 are signed in their own realm (`~cache`), which no run id can equal, so an artifact upload URL cannot write into the cache. The `CacheMetadata` of v2 requests (repository id and scopes) is ignored. Matching follows the docs: per key in order, an exact match wins, else the newest entry whose key starts with it, within the same `version`. Entries are immutable once committed (409 on a second reservation; an unfinished reservation older than an hour is replaced). Chunks are placed by `Content-Range`, wait on disk (in a private directory made by `azblob.NewSpoolDir` under `Config.SpoolDir`, which `raccoonci run` puts next to the store, never in a small `/tmp`; the artifact service does the same), and are cut into `partSize` parts at commit, because the client picks the chunk size (`upload-chunk-size`) and the store needs 5 MiB parts. Committed entries are listed in `index.json`, so a cache outlives the process; `raccoonci run` keeps it under `<user cache>/raccoonci/actions-cache/<hash>-<repository>/`. An entry whose object has vanished from the store is dropped at lookup. Verified end to end with the real `actions/cache@v4` and `actions/cache/restore@v4`, two jobs each: v1 with 20 MB in 1 MiB chunks and a second process that hit the first one's entry; v2 with 20 MB (one Put Blob, also hit by a second process) and 150 MB (above the SDK's 128 MiB single-shot limit, so sent in blocks). `Config.MaxBytes` caps the committed entries (`raccoonci run -cache-limit-gb`, default 10 like GitHub, 0 = none): when a new entry would exceed it the least recently used go first (`record.Used`, updated on a lookup hit and saved with the index at the next commit), and an entry larger than the cap is refused (400 at reserve or commit, `ok: false` in v2). `Config.Free` (a `statfs` of the store's disk in `raccoonci run`) is checked before an entry is assembled: older entries are evicted until it fits with 256 MiB to spare, otherwise the commit fails with 507. With v2 the data is stored before Finalize, so eviction happens after it. `raccoonci run -cache-s3-bucket …` (`cmd/raccoonci/cachestore.go`) keeps the entries in an S3-compatible bucket instead of on the controller's disk: `startCache` then gets a `blob.S3` store with the prefix `<-cache-s3-prefix><repository dir>/`, no `Free` check, and clients download from presigned bucket links; credentials come from `RACCOONCI_CACHE_S3_KEY`/`_SECRET`/`_TOKEN`. `blob.S3.PutPart` reads a non-seekable part up to 32 MiB into memory so the SDK can retry it. Verified against SeaweedFS's S3 gateway, not a real external bucket. Not done: scoping by branch (every ref of a repository shares one cache), concurrent `raccoonci` processes writing one index (last writer wins), and a separate secret for the cache's download links (it shares the run's key).
- `pkg/dispatch`: sends a job to a machine over a connection the machine opens (`raccoonci agent`). `Controller.Submit(Job)` returns a `Run` with a random token; the agent presents it as a bearer token on `GET /v1/job`, `GET /v1/source` (the source tree as .tar.gz, `TarDir`), `POST /v1/log` (chunks at `X-Offset`: a resent chunk only writes its new tail, a gap is a 409 with `X-Expected-Offset`), `POST /v1/heartbeat`, `POST /v1/done`. The controller keeps only the token's SHA-256, so a token opens its own job only, and there is no unauthenticated route (the address may be public). `Run.Wait` fails when the machine never calls (`StartTimeout`, 2 min) or goes silent (`Lease`, 30 s). The agent runs `raccoonci run [-secret NAME…] <Job.Args>` as a subprocess in the unpacked source, with `Job.Env` and `Job.Secrets` in its environment, and ships stdout and stderr; it refuses a controller URL that is not https (or http on a loopback address), because the token and secrets travel on it. Config is read from a file (`/etc/raccoonci-agent.json`, polled until it appears), never the command line. The reason for this shape: InstaBox allows 32 concurrent exec requests across the account, and a machine has no inbound address. Not done: returning artifacts and caches from the machine, secrets other than plain in the assignment.
- `pkg/instabox`: the part of the InstaBox API we use (`Client`: create from a snapshot and wait for the operation, `PUT /files`, exec, delete with `X-Confirm-Delete`, delete snapshot; the key goes only in `X-API-Key`; the API's OpenAPI spec is public at `/v1/openapi.json`) and `Provider.Run`, which makes a machine with `deleteAfterSeconds` (the server deletes it even if this process dies), writes the agent's config through the file API, waits on `dispatch.Run`, and always deletes the machine (not with the cancelled ctx). `raccoonci run -on instabox -listen ADDR -controller-url https://… -snapshot ID` serves the controller and the artifact/cache services on ADDR (the user publishes it, e.g. with `instabox-port`; every link and env value is built on `-controller-url`, `publicServe`) and sends each job instance to a machine of its own: the engine here resolves needs and matrices and hands every instance to `engine.Options.Remote` (after the `max-parallel` slot; unavailable OSes still fail here without a machine); the machine's agent runs `raccoonci run-instance`, which reads an `instanceSpec` from stdin (workflow path, job id, github/matrix/strategy/needs/inputs/vars as JSON, service env) and calls `engine.RunInstance`, then prints `wireLine`s (events, then the result with outputs) that `wireReader` turns back into `runner.Event`s for the local printer. `-secret` values are read locally and travel in the assignment. `-parallel` defaults to 8 in this mode. All instances share one service token, so a job on a machine can read the whole run's artifacts. The runner snapshot's systemd unit `raccoonci-agent` waits for `/data/home/.raccoonci-agent.json`. Every non-GET call carries a fresh `Idempotency-Key` (the API requires it). The key is read from `INSTABOX_API_KEY`, else `IBX_API_KEY` (the first name is reserved on InstaBox machines, so an org Secret has to use another). Each instance gets a service token of its own (`services.jobEnv`: the job id in the token's scope is `<job>-<n>`), so a token creates artifacts only as its job; the run's other artifacts stay readable, as on GitHub. The source package leaves out what git ignores (`git ls-files --others --ignored`; `.git` stays; no git means nothing is skipped). `raccoonci runner-snapshot` (`Client.BuildRunnerSnapshot`, `make runner-binary` for the static binary) rebuilds the runner snapshot: clean `universal` machine, binary + agent unit + manifest installed, version and static linkage checked on the machine, snapshot, machine deleted. Verified end to end with this repo's own `ci.yml`: job 1m15s, whole command 1m35s including machine create, upload and delete.
- `pkg/trigger`: whether an event starts a workflow, from `Workflow.On`. `Match(on, Event)` handles the three spellings of `on:`, `types` (pull requests default to opened/synchronize/reopened), and for push and pull requests GitHub's filters: `branches`/`tags` and their `-ignore` forms (a push of a tag with only `branches` listed does not trigger, and the reverse; a pull request's branches apply to its base; both a filter and its `-ignore` is an error), and `paths`/`paths-ignore` (tag pushes skip them; `Event.Files == nil` means unknown, so the filter does not block). Patterns are GitHub's own globs, not shell globs (`glob.go`): `*` stops at `/`, `**/x` also matches a top-level x, `?` and `+` act on the character before, and in a list `!` deselects what came before, later positives select again. `Schedules` and `DispatchInputs` (defaults, required, choice, typed boolean and number, unknown inputs refused) round it out. The CLI side is `match.go`: `raccoonci match` and `run -only-if-triggered` fill the Event from the checkout (branch, `HEAD~1..HEAD`) unless flags say otherwise; plain `run` still assumes the event fired.
- `pkg/wire`: what a controller and a machine say besides the dispatch protocol: `InstanceSpec` (the job instance to run, read by `raccoonci run-instance` from stdin), `Encoder`/`Reader` for the lines the machine prints (events, then the result with outputs). Used by `cmd/raccoonci` (as aliases in `instance.go`) and by the server; it is the contract between runner and backend, so it will live in a shared repository.
- `pkg/affected`: which jobs the changed files concern (Raccoon CI's own extension; reads the optional `.raccoonci/affected.yml`). Data only; the cli uses it.
- `pkg/jobgraph`: the job graph, and nothing that runs a job (a guard test keeps its dependencies to data packages: catalog, expr, platform, runevent, value, workflow). `Run` orders jobs by `needs`, evaluates `if:`, expands matrices and hands each resolved instance to `Options.Remote`; `OnEvent` receives the graph's own events. `RemoteInstance` carries `Context`/`RunsOn` for the executor. The backend (`backend`) uses only this, not the runner's engine.
- `pkg/archive`: tar.gz extraction through `os.Root`. Entries can't escape the destination via `..`, absolute paths, symlinks or hard links.

## The GitHub Runner path and job scheduling (`pkg/ghrunner`, `pkg/sched`)

Moved here from the cli repository on 2026-11-03 (their history came with them): they are shared code, used by the cli's `serve` and `run -on instabox` commands and possibly by the server later. The `ghrunner` tests take about 45 s.

- `pkg/sched`: decides which job instances share a machine. `History` keeps the last 5 on-machine durations per workflow file and instance name (a JSON file under `<user cache>/raccoonci/sched/`, replaced atomically; a damaged file reads as empty). `Policy.Short` says an instance is short when its median is under 3 times the median start-up measured in this run (10 s before any machine has come up). No history means long: packing a long job costs it CPU, a lone short job costs one start-up, and the history corrects the next run. `instabox.Pool` runs the short ones: it fills a machine up to its slots (default one per vCPU, learned from the first machine; `-pack-slots`) before creating another, keeps an empty machine 15 s, and deletes all at `Close`. Each slot has its own agent config file (`dispatch.SlotConfig`), written by the pool and deleted by the agent when read, so the runner snapshot's agent runs `agent -loop -slots 8`. Instances with `container:`/`services:` or that can start from an environment snapshot are not packed. `-no-pack` turns it off. Not done: fixed-port clashes between packed jobs, a warm machine pool, real-benchmark numbers (see `TODO.md` C.3).
- `pkg/ghrunner`: the GitHub-triggered path, `raccoonci serve`. GitHub keeps triggering and orchestrating (so every workflow feature works as there); we only supply runners.
  - **Flow.** `Client` (GitHub REST; every GET sends the ETag back, a 304 costs no rate limit, which is what lets it poll every second) lists queued and in-progress runs per repository (`ActiveRuns`, `RunJobs`); a queued job with a label starting with `-label-prefix` (default `raccoon-`) gets a just-in-time runner (`generate-jitconfig`, runner group 1) and a machine from the InstaBox `ci` template (Ubuntu 24.04, GitHub's own runner image with the runner 2.338.2 at `/opt/actions-runner`, unconfigured). Both are created in parallel; the JIT config is written to the machine with `PUT /files` (mode 0600) and read by `run.sh --jitconfig "$(cat file)"`, so it is never on a command line or in a log (a test asserts it). `follow` polls the runner each second until GitHub removes it (a JIT runner is single-use), then the machine is deleted. A job that finds no runner within `IdleTimeout` (3 min) is given up on, up to 3 attempts. A runner started for a job whose job another (waiting) runner took is released after about 10 s (`takenCheckAfter`), not after the timeout.
  - **Idle runners** (`keepalive.go`, `docs/research/idle-runners/` in the cli repository has the model, a simulator and the numbers measured on real traces). A waiting runner is a running machine (about $1 a day for 4 vCPU / 8 GiB), but a job that finds one starts in about 1 s instead of 10 s. `KeepAlive` decides how many to keep after jobs have come: the cost of a waiting second is `C`, the worth of a second of a job waiting is `V` (`-second-value`, default $0.01, 0 turns the policy off), a refill takes `R` = 8 s, and a hit saves `Δ` = 8 s. Per gap between bursts of arrivals (bursts within 30 s are one) it keeps a runner for the TTL that minimises cost + V×latency over the last 100 gaps; before 20 gaps it uses the ski-rental break-even `V·Δ/C`. The pool size follows the burst size (EWMA, at most 4). `Service.Idle` is a floor. Surplus waiting runners are retired (their registration is deleted first, which GitHub refuses for a runner that has a job, so retiring is safe).
  - **Known arrivals** (`prestart.go`, `cron.go`) need no policy: a workflow's `schedule:` cron is read from the repository's workflows (re-read every 10 min; `ParseCron` is UTC with lists, ranges, steps, dom/dow OR) and a runner is started `R` seconds before each fire time and kept until +10 min (GitHub starts scheduled runs minutes late). A job that `needs` a job in progress gets a runner just before the running one is expected to finish, from the median of its last durations (`sched.History` under `<user cache>/raccoonci/serve/durations.json`, keyed by repository and job name; recorded from completed jobs); no known duration means no guess. Both are `expectation`s.
  - **Step progress** (`progress.go`): the jobs API lists a job's steps with their status, so the time a running upstream job has left is what its unfinished steps take (each step's median, remembered per repository, job name, step number and name when a job completes; the step it is in counts for its median less what it has run, and a step that has overrun its median counts as done at once, so the estimate leans early) instead of the whole job's median; a step with no history falls back to the job median. A run with a job waiting for one still running is `track`ed and looked at every second (`refreshTracked`, ETag requests) even when webhooks make the normal listing come every 30 s, and an expectation seen again has its moment updated. When a job a runner was started ahead for is first seen, `reportPrediction` logs how far each estimate (steps, and the job median alone) was from the time GitHub queued it. Measured live (2026-11-01, a `build` with one random 5–24 s step and a `deploy` that needs it, 8 predictions, a deliberately noisy case): mean absolute error 5.3 s by steps and 5.0 s by the job median, but by steps the runner was never late (errors −9 to −2 s) while by the median 4 of 8 were late (up to +9 s, which with about 7 s to start a runner means a cold start); the downstream job started 1 s after being queued in every run with history. Early costs about 10 s of a machine, late costs a cold start of 6 s, so not being late matters more.
  - **Matrix jobs** (`matrix.go`): a job with a matrix is queued as one job per combination, all at once, so `instancesOf` says how many runners to start ahead: a matrix written out in the workflow is counted with `workflow.ExpandMatrix`; one with a `${{ }}` in it (`fromJSON(needs.plan.outputs.x)`) is not known until the job that builds it finishes, and GitHub's API does not return job outputs (to my knowledge), so the **largest** of the last five counts seen on earlier runs (`recordCount`, kept in `sched.History` as that many seconds, once per run and job) stands in for it. Largest, not median, because a runner too many waits about 15 s (a fraction of a cent) and one too few leaves a job a cold start of about 7 s: on eight live runs of a matrix of 2 to 5 jobs (counts 2 4 3 2 2 5 5 4) the median left 8 of 25 jobs to a cold start and wasted 2 runners (live), and the maximum, run live at one run every 100 s (7 runs with history, counts 4 2 5 5 4 4 4), left 1 of 28 jobs to a cold start and wasted 5 runners. **It only holds while the start limit is not tight**: at one run every 62 s (5 to 6 starts per run against 10 a minute) the limit kept back part of the runners started ahead and the maximum did no better than the median (about 30% of jobs cold in both); the log line `N of those M runner(s) not started: the start limit …` says when that happens (before it was silent). Capped by `max-parallel` and by `MaxJobs`; no history means one. An expectation carries the count and starts that many together.
  - **Start limit** (`starts.go`): InstaBox lets an organization start a limited number of machines a minute (10 on the Pro plan; the API refuses with 429 beyond it). `serve -starts-per-minute` (default 10, 0 = no limit) makes the service count its own starts in a sliding 62 s window and keep the last three for jobs that are queued: a runner started ahead of a job that is not queued yet (`speculative`) may not use them. A start refused by our count or by a 429 does not use up an attempt of the job: it is asked again after a wait (`serving.notBefore`, `startHold` 20 s after a 429, which also holds all starts). Before this, three quick 429s gave a job up for good and it stayed queued for ever. Warm runners do not use starts, which is part of what keeping them is worth when a matrix fans out.
  - **Runners are interchangeable.** GitHub gives a runner the oldest queued job that its labels fit, not the job it was started for, so with a backlog or a fan-out a job can be left queued after the runner started for it has run another one. `startFor` looks at the job when its runner has gone and, if it is still queued, asks for another runner (the attempt is not used up if the runner did work). Also, only runners kept waiting count as free (`idleCountLocked`, `launching`): one started for a job is spoken for, and counting it had given the fourth job of a fan-out a promise to the runner of the third and made it wait the 20 s the promise lasts. Each of these three was found by a live run and has a test that fails without the fix.
  - **Pools.** Without `-org` each repository has its own pool and its runners are registered with the repository. With `-org` (one loop for all the repositories watched, all of the organization's when no `-repo` is given) the runners are registered with the organization (runner group 1, `Default`; its visibility must include the repositories, and a public repository needs the group to allow public ones), so a waiting runner takes a job of any repository: the biggest saving in the research, since one repository's burst keeps a runner for the others. `poolOf(repo)` is the one place that maps a repository to its pool; `liveRunner.repo` is the pool's scope (`org:<name>` or the repository), `liveRunner.jobRepo` where the job is. A runner of the organization can take any job with the labels, from any repository of the group, so repositories that do not trust each other must not share a pool.
  - **Machine size** (`size.go`): a job's `runs-on` label `raccoon-<N>vcpu` asks for N vCPUs; the memory is the one InstaBox gives that many (the sizes the organization may create are read once from `GET /v1/orgs` `allowedSpecs`; this account has 2/4 GiB, 4/8 GiB and 8/16 GiB), passed to the machine create (`Provider.AcquireSize`, `CreateRequest.VCPUs/MemMiB`). A label with no size gets the default size. A size that cannot be created (`raccoon-64vcpu`) is not left queued for ever: the service logs what the organization can create and cancels the run (`SizeError`). A waiting runner has only the labels `self-hosted` and the service's runner label (`raccoon-4vcpu`), and GitHub gives a job only to a runner with every label it names, so `consider` counts a waiting runner as able to take a job only when `waitingCanServe` (all the job's labels are those), and schedule and downstream anticipation skip jobs it would not serve: other sizes always get a machine of their own, with the cold start; keep-alive per size is not done. `serve -runner-label raccoon-2vcpu` makes the waiting runners that size (the machine size of a waiting runner follows its label), so one service keeps one size warm; that is how the 2-core comparison with GitHub-hosted runners was run. If reading the sizes fails, jobs of the default label still run (default size). Verified live: `raccoon-8vcpu` got `nproc` 8 and 16 GB; `raccoon-64vcpu` was refused with the message and the run cancelled, no machine created.
  - **Where a cold start goes** (measured 2026-10-31 from the runner's own log on the machine; `queued→started` 6–9 s against GitHub-hosted 2 s): machine create 1.6 s, the runner process starting 1–2 s, the runner authenticating and opening its session with GitHub about 2 s, GitHub handing it the job about 1 s, our own noticing under 0.5 s. A paused spare (`-warm`) no longer helps: resume takes 1.6–3.2 s against 1.6 s for a create, and the runner's own start-up is no faster on a warm machine, so `-warm` is off by default and should stay so. What is left is mostly GitHub's runner protocol; it can be hidden (an idle runner: 1–2 s) but not removed.
  - **Measured on InstaBox** (jobs queued→started as GitHub reports it): machine created for the job 10 s then, 6–9 s on 2026-10-31 when a create takes 1.6 s; paused spare (`-warm N`) 7–9 s; idle runner already online 1–2 s. GitHub-hosted runners were 3–4 s and InstaBox's own `instabox-medium` 12–20 s. Verified live: a chain `a → b → c` on `bench-lint-docs` (second run: b and c 2 s, the runners having been started 8 s before they were due); a job of `bench-go-integration` started in 2 s on a runner kept after a job of `bench-lint-docs` (organization pool). The keep-alive policy, the downstream prestart and the release of a taken job's runner have unit tests (fake GitHub and InstaBox); the live runs used a small number of runs, so the policy has not been evaluated on a real workload.
  - **Webhooks** (`webhook.go`, `cmd/raccoonci/webhooks.go` in the cli repository; `serve -webhook-listen ADDR -webhook-url https://…`): the user publishes ADDR (the sandbox's `instabox-port publish` needs the user's permission), `serve` makes a random signing secret (memory only, never printed), creates or updates one repository webhook per watched repository for `workflow_job`, `push` and `pull_request` events (needs `admin:repo_hook`; an existing hook with our URL is updated, others are not touched) and deletes them when it stops. `Webhook` rejects anything whose `X-Hub-Signature-256` (HMAC-SHA256 of the body, constant-time compare) is wrong before reading it; a delivery for a repository not watched, or before/after `Run`, gets 202 and the listing finds the job anyway. A `queued` job goes straight to `Service.consider` (the same decision a scan makes, so a redelivery or the scan finding it too starts nothing twice); `in_progress` and `completed` clear the promise a waiting runner made for the job and wake the loop to scan (durations, downstream jobs). With webhooks the repositories are listed only every `-safety-poll` (30 s); runners to start ahead or to let go are still checked every second, which costs no request. `consider` also fixed that a job whose launch failed was never retried. Unit-tested with fake GitHub and InstaBox (signature, a queued job started with the listing set to an hour, redelivery, foreign repository, hook registration and removal); verified live (2026-10-31, `bench-lint-docs` chain `a → b → c` pushed twice through a published port): GitHub's ping got 204, an unsigned POST through the public URL got 401, the job's runner was started 1.4 s after the delivery (machine 1.1 s), a cold first job started 7 s after being queued and the others 1–2 s, and the hooks, runners and machines were all gone after `serve` stopped.
  - **Events that are about to start workflows** (`event.go`): the webhook also takes `push` and `pull_request` (the hook is made for `workflow_job`, `push` and `pull_request`). On one, `anticipate` lists the repository's workflows, reads each at the event's commit, asks `trigger.Match` whether the event triggers it (branches, tags, `paths` from `ChangedFiles` through the compare API, or unknown when that cannot be had, activity types), counts the first jobs that need nothing, carry our label and which a waiting runner can serve (`instancesOf`, so a matrix counts as its jobs), and makes an expectation for that many runners, starting them at once and keeping them a minute. Measured live (2026-11-01, six pushes to a workflow on `bench-lint-docs`): GitHub queued the first job 2–3 s after the event reached us (every time), and with a runner started ahead that job began 5–7 s after being queued, against 6–9 s for a cold start: **about 1–2 s gained**, six runs, within the noise, one runner of the six unused. A runner needs about 7 s from its start to taking a job and GitHub gives only 2–3 s of that head start. The log says `the first job of the run for … was queued N s after the event reached us`. A pull request is read at its head commit, because `refs/pull/N/merge` does not exist yet when the event arrives (404 right after opening; `refs/pull/N/head` can be read).
  - **Which workflow file a run uses** (`workflowOfRun`): for most events the file at the run's `head_sha`; for `pull_request` (its merge commit), `pull_request_target` (the base branch) and `workflow_run` (the default branch) the ref after the `@` in the run's `path`, with the commit as a fallback if that cannot be read. `workflowFile` keeps what it read for good only when the ref is a full commit id, else for 5 minutes (it used to keep a branch for ever, so a changed cron on `main` was never seen). The path-ref reading is tested with a fake GitHub, not yet seen on a real pull request run.
  - **Not done / not verified:** organization-level webhooks (`admin:org_hook`; the repository hooks are one per watched repository); whether InstaBox's auto-suspend (30 min) treats a machine with a listening runner as idle; a real `schedule:` fire (cron is unit-tested only); `actions/cache` and artifacts go to GitHub's services on this path, redirecting them to `pkg/cache` is untried; a `pull_request` event on real GitHub (only `push` was run live); the `if:` of a job is not evaluated when counting runners to start ahead (a job that will be skipped still gets one); keep-alive and pooling per machine size; the number of machine starts a minute (10 on InstaBox's Pro plan) is what limits a big fan-out, and the user is looking into raising it.
